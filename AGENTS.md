# AGENTS.md: working on Distiller

This file is for AI coding agents and the people who direct them. It explains what Distiller is, how the code is organised, how to build and test it, and the rules every change must follow. Human contributors should read it too; `README.md` covers using the app, `CONTRIBUTING.md` the contribution process (with the issue and pull request templates in `.github/`), `SECURITY.md` what counts as a vulnerability and how it's reported, and `CODE_OF_CONDUCT.md` how everyone is expected to behave. Keep `SECURITY.md`'s list of security promises in step with the rules below.

The maintainer keeps local, untracked documents in `docs/` (the design notes, and `docs/HANDOFF.md` with session notes: what was built recently, what's being verified on real hardware, open decisions). If `docs/HANDOFF.md` exists, read it at the start of a session and update it at the end. **Never commit anything in `docs/`** (it's in `.gitignore`), and never copy its private details (people's hardware, file paths on their drives, account or certificate names) into tracked files.

## What Distiller is

Distiller is a native SwiftUI app and a command-line tool for installing and running Windows games on Apple silicon Macs with Wine. It's driven by **recipes**: declarative, shareable YAML that says which Wine build and graphics translation layer a game needs, which winetricks verbs, registry settings, DLL overrides and environment variables, and how to adjust them for different Macs (**hardware overlays**). Players create recipes in the app, prove them with a **community check**, and share them through the companion repository **distiller-recipes**, whose published catalogue the app (Community tab) and the website read.

This file is the shared reference for the architecture and the rules; the recipe format is defined by the schemas in the recipes repository.

## Commands

- Build: `swift build`
- Test: `swift test` (a few seconds). The disk-image importer tests (`GPTKImporterTests`, real disk images made with `hdiutil`, about 45 s and unreliable on CI machines) are skipped unless `DISTILLER_SLOW_TESTS=1`; run them when you change `GPTKImporter`. CI builds in debug, so also check a release build (`swift build -c release`) after large SwiftUI changes: release builds can fail with "unable to type-check this expression in reasonable time". Split long view bodies into properties and `ViewModifier`s.
- CLI: `swift run distiller <command>`; `swift run distiller --help` lists them (hardware, setup, components, bottles, run, recipe …, install, games, launch, community, github, storage, mcp, assistant, logs).
- App without bundling: `swift run DistillerApp`. As a bundle: `Scripts/bundle-app.sh [debug|release]` builds `dist/Distiller.app` with its icon.
- Website: `node --test site/tests/*.test.mjs` tests its data module; preview with `python3 -m http.server --directory site` (it fetches the live catalogue).
- Isolate experiments: `export DISTILLER_HOME=/tmp/distiller-dev` gives the engine its own support folder and `settings.json`, so experiments never touch a real library or real bottles.
- App icon: edit `Design/AppIcon.svg`, then run `Scripts/make-icon.sh`.
- Version: major.minor.revision. Each release takes the newer of `VERSION`'s major.minor and the newest release tag's, or the Release run's **Major**/**Minor** fields when set, and the next revision from the release tags (`Scripts/next-version.sh`, which refuses a major.minor older than a release). So a new major or minor can be set when starting a release; `VERSION` (changed in a pull request with `Scripts/bump-version.sh`) is a floor that can catch up later. `bundle-app.sh` puts the version in Info.plist (`CFBundleShortVersionString`, plus `DistillerVersion` with any suffix such as a dry run's `-dev.<sha>`), and `DistillerVersion.current` reads it back in the app and the CLI (`distiller --version`, the MCP server). Don't hard-code a version anywhere else.
- Releases: run `.github/workflows/release.yml` by hand on `main` (Actions ▸ Release ▸ Run workflow, or `gh workflow run release.yml`); after the owner approves, it builds, signs, notarizes, then tags `v<version>` and publishes. Only the workflow creates `v*` tags. Every release attaches the disk image as `Distiller.dmg` too, and the website and README download it from `releases/latest/download/Distiller.dmg`; don't rename it. `RELEASING.md` explains the setup.

Shells that run under Rosetta (an x86_64 shell, for example one started from an Intel-only Homebrew bash) can't load the arm64 test bundle ("doesn't contain a version for the current architecture"). Run `arch -arm64 swift test` there; `uname -m` shows `x86_64` in an affected shell.

`Scripts/bundle-app.sh` signs with `DISTILLER_SIGN_IDENTITY` if set, otherwise the first "Apple Development" identity in the keychain, and ad hoc only as a last resort. macOS ties privacy permissions (Screen Recording, used for community-check screenshots) to the signature, and an ad-hoc signature changes with every build, so a permission granted to one build doesn't carry over to the next.

## How to work

- **Pull requests only.** `main` is protected: every change arrives as a pull request from a branch, reviewed and approved by a code owner, with the test workflow passing. Never push to `main`, force-push, or rewrite published history. Name branches by what they do (`fix/…`, `feature/…`, `docs/…`).
- **Keep the tests green and add tests with every change.** New behaviour gets tests; bug fixes get a test that fails without the fix. Network code is tested against in-process fakes (for example `FakeGitHub`, a route-based `URLProtocol` in `SubmitterTests.swift`), never against live services.
- **Small, focused changes.** One concern per pull request. Explain what changed and why, and how you verified it (tests, and on real hardware if it touches Wine, graphics layers or the file system).
- **Ask before changing direction.** Design decisions (the recipe format, the security model, what is shared publicly, licensing, the submission flow) belong to the maintainers. Propose options with trade-offs; don't silently pick one.
- **Don't run destructive or outward-facing actions on someone's machine or accounts without their explicit go-ahead**: deleting bottles or games, moving storage, signing in, pushing, opening or merging pull requests, publishing.
- **Don't quit or relaunch the app while a community check might be running** (`pgrep -lf wine` shows Wine processes). Quitting mid-check skips its cleanup and leaves a large test bottle behind (the app offers to remove such leftovers at its next launch).
- **Update the docs you affect**: `README.md` for user-visible behaviour, this file for new rules or architecture, and the local `docs/HANDOFF.md` (if present) for what you did.

## Architecture

- **One entry point.** `DistillerEngine` is the only API the app and the CLI use; both stay thin, so anything the app does can be exercised from a terminal and from tests.
- **Components.** Wine builds and graphics layers are versioned components with a `component.json` manifest, downloaded from their publishers' releases and checked against the release's SHA-256 digest, or imported from a folder or archive the player chose. `EnvironmentSetup` checks for and installs Rosetta, Wine, winetricks, cabextract and the open-source graphics layers; host commands come only from its fixed list, never from recipes.
- **Sources** (`Components/ComponentSource.swift`, `Components/SourceInstaller.swift`, `Support/MachODependencies.swift`, `AppModel+Sources.swift`, `AddSourceView`, `SourceSubmitter.swift`). Recipes name Wine builds by tag (`stack.runner.family`); a `ComponentSource` (YAML, the format of `components/<kind>/<tag>.yaml` in the recipes repository) says where one comes from (`get.github_release`: repository and a file pattern whose first group is the version), its publisher, homepage and SPDX licence, what it provides (family, arch), `libraries_from` (another source whose installed build supplies libraries it leaves out) and `contains_d3dmetal`. `ComponentSources`: Distiller's own (`builtIn`, from `WineSource` and `GraphicsLayerSource`) plus the player's (`DistillerPaths.sources`, `saveSource`; a built-in tag can't be replaced). `missingComponents(for:)` finds a family nothing installed provides and no built-in source covers; installing a recipe (`AppModel.install`) first asks the player to describe or install it (`MissingSourceSession`): Find Files lists the repository's release files (`releaseFiles`), choosing one makes the pattern (`pattern(forFileName:)`), and `EnvironmentSetup.install(_:file:)` downloads it only with GitHub's checksum, installs it, clones the shared libraries of the `libraries_from` build (its `lib/` and GStreamer framework) that it lacks into its `lib/wine/x86_64-unix` (`SourceLibraries.folder`: Wine's Unix side finds them there, `@loader_path`) and records that folder as the build's `library_paths`, which `WineEnvironment.build` gives Wine as `DYLD_FALLBACK_LIBRARY_PATH` (set last; recipes can't change it) for programs with no search paths of their own (Sikarugir's `wineserver`, made for an app that sets it). macOS drops `DYLD_*` when it starts a system shell, so winetricks gets wrapper scripts as `WINE`/`WINESERVER` that set it again (`WineEnvironment.scriptWrappers`). The install then refuses (and removes) a build whose programs can't find an `@rpath` library through their own `LC_RPATH`s (`@loader_path`, `@executable_path` = `bin`), their folder (for libraries) or the library folder (`MachODependencies.missingRPathLibraries`), and reports D3DMetal and macOS-driver exports. `distiller sources check <build>` runs the same check. Vulkan driver manifests (`share/vulkan/icd.d/*.json`, MoltenVK's) come with the libraries, their `library_path` pointed at the copied driver and `is_portability_driver` turned off (the Vulkan loader hides portability drivers from programs that don't ask for them, and Sikarugir's Wine doesn't ask: "Found no drivers"), and `WineEnvironment.build` sets `VK_DRIVER_FILES`/`VK_ICD_FILENAMES` to them for such builds (Gcenx's Wine Staging points its loader itself; Sikarugir's engine relies on its app to): without them Vulkan can't start ("failed create vulkan instance: -9"), and nor can DXVK or games' Vulkan renderers. `distiller sources repair <tag>` adds what an installed build (and the builds composed from it) is missing and updates driver manifests copied by earlier versions. `RecipeSubmitter.submitSource` opens a pull request adding the source file (fork or maintainer branch, never the base branch; a published source isn't replaced). Only Wine sources install this way for now. CLI: `distiller sources list|files|add|install|check`.
- **Graphics layers.** D3DMetal (imported from the player's own Game Porting Toolkit download), DXMT and DXVK for macOS ("builtin" archives rearranged to `lib/wine/<arch>`) are merged into a clone of a Wine build by `StackComposer` (`placement: wine_lib`); prefix-DLL layers are copied into the bottle by `GraphicsPlacer`. WineD3D needs nothing extra.
- **Component updates and active versions.** `settings.json` `component_updates` (`ComponentUpdateMode`: `ask`, the default; `auto`; `off`) decides whether the app checks once a day (and at launch) and whether it installs what it finds; checking by hand works in every mode. `EnvironmentSetup.checkForUpdates` compares the newest installed version of each component that came from a known source (`WineSource`, `GraphicsLayerSource`, winetricks) with that source's latest release; a source that fails doesn't stop the others. Each component id has one **active** version (`ComponentStore.activeComponents`): the newest, unless the player chose another (`active_components`; `makeActive` clears the choice when they pick the newest). Lookups (`wineCandidates`, `graphicsLayer`, `winetricks`) put the active version first, so new games use it and bottles move to it when they can (a bottle's Wine never goes back). An update installs alongside and becomes active; a held component (an older version chosen as active) is skipped by automatic updates. `ComponentCleanup` removes versions nothing needs: not active, downloadable again (imported components such as D3DMetal are never removed automatically), and, for Wine, not the only build that can still open some bottle; with them go the composed builds and the template made from them, and anything a running process uses is skipped.
- **Per-game versions** (`Bottles/DistillerEngine+Versions.swift`). A bottle follows the active version of each component unless `bottle.json` `stay_on` names one (`Bottle.StayOn`: wine, graphics, winetricks as id@version; a choice on this Mac, never in a recipe). `chooseWine` uses exactly the kept Wine, `graphicsLayer(_:for:)` the kept layer when it provides the game's backend, `RecipeInstaller.winetricks(for:)` the kept winetricks; a kept version that's missing fails with a message pointing to Follow Updates. `setStayOn` refuses a Wine the bottle can't use (older, or another kind). Bottles record the graphics layer and winetricks they last used (`graphics`, `winetricks`). `ComponentCleanup` never removes a version a game stays on.
- **Restore points** (`Bottles/RestorePoints.swift`). When a run would move a bottle to a newer Wine (`pendingWineMove`: it follows updates and a newer build is active), `prepareWineMove` first clones the prefix to `Bottles/<id>/restore/` (one per bottle, with `restore.json`), then updates it with the new Wine (`wineboot -u`, with progress) and records the move; if that fails, the copy goes back. The app and the CLI call it before launches, installers and Wine tools. After the first session the app asks once whether the game works (`markRestorePointAsked`): `confirmWineMove` removes the copy (or marks it, when kept until removed), `rollBack` puts it back and keeps the game on the old Wine (`stay_on`). `settings.json` `restore_point_days` (default 7; 0 until confirmed; -1 until removed) and `expireRestorePoints`, run on every reload. `ComponentCleanup` keeps the Wine a restore point needs.
- **Rebuilding a bottle** (`Bottles/DistillerEngine+Rebuild.swift`). `rebuild` installs the game's recipe (with its local overrides) into a new bottle with the active components; only on success does the game switch to it (`Game.rebuild` records the previous bottle). Failure or cancellation removes the new bottle and leaves the game untouched. `rebuildItems` reuses what the old bottle has for `user_file`, `user_download` (still verified) and `user_folder` steps (a linked folder is linked again; a copied one is cloned); the app asks only for the rest. `keepRebuild` trashes the old bottle, `switchBack` returns to it and trashes the new one; the app asks once after the first session, and removing the game removes both bottles. Nothing inside the old bottle (saves, settings, sign-ins) is carried over, and the UI says so before starting. Tests set `BottleStore.deletesToTrash = false` so runs don't fill the Trash.
- **Distiller's own updates** (`Support/AppUpdate.swift`). The repository a build updates from is baked in at build time (`DistillerUpdateRepository` in Info.plist: `GITHUB_REPOSITORY` in Actions, else the checkout's origin, else `DISTILLER_UPDATE_REPOSITORY`), so forks update from themselves; **never hard-code a repository**. `AppUpdater` reads that repository's latest release, downloads `Distiller.dmg` and refuses it unless it matches the release's `SHA256SUMS.txt`. `AppBundleCheck` mounts it read-only and refuses the app unless it has the same bundle identifier, the release's version, a valid `codesign --verify --deep --strict` signature, the **same team identifier as the running copy** (`SecStaticCode`; an unsigned copy has nothing to compare and can't self-update), and Gatekeeper's approval (`spctl`: Developer ID, notarized). `AppReplacer` copies it next to the running app (`ditto`), moves the old copy to the Trash, moves the new one into place (putting the old one back on failure), and reopens it after the app quits; apps in a read-only or translocated location get the checked disk image opened instead. The app checks with component updates, announces a version once, and installs only on the player's click, never while games, installs or community checks run. Release workflows must keep publishing `Distiller.dmg` and `SHA256SUMS.txt`.
- **Wine capabilities.** D3DMetal and DXMT need a Wine build whose `winemac.so` exports the macOS driver's `macdrv_*` functions; many upstream builds hide them. `WineCapabilities` (`Support/MachOExports.swift`, a bounds-checked Mach-O export-trie reader) detects this, `availableGraphics()` and `selectStack` respect it, and a recipe must never launch into a layer its Wine can't run.
- **Bottles.** A bottle is a Wine prefix for one game, an APFS clone of a per-Wine-build template prefix (`BottleStore.ensureTemplate`), so a bottle per game costs almost no space. A bottle keeps to the Wine that made it: `chooseWine(for:bottle:)` allows only the same build or family at the same or a newer version (Wine upgrades a prefix in place but can't go back). Anything that runs in an existing bottle must pass the bottle (`selectStack(for: game, recordUpgrade:)`).
- **Resolution order.** Built-in defaults → component manifest (`WineEnvironment`) → recipe → matching hardware overlays in file order → the player's local overrides.
- **Storage.** The support folder always holds `library.json`, `Logs/`, `RecipeCache/`, `Icons/`, `CommunityMedia/` and `settings.json`, `Performance/` once something is recorded, and `Sources/` for sources the player added. Launch logs in `Logs/` are size-limited (`LaunchLog`: the first 20 MB and the last 4 MB, with a note in between), and MoltenVK reports errors only by default (`WineEnvironment.defaults`), because some games print the same warning many times a second. `LogCleaner` keeps the folder in check (`settings.json` `log_retention_days`, default 14, and `log_limit_mb`, default 1024; 0 turns either off): the app cleans up when it starts and once a day, Settings ▸ Storage ▸ Logs and `distiller logs` show and change it, and logs written in the last hour are never removed. Players can put Wine builds and bottles (bottles and templates together, because clones only work within a volume) on other drives. Locations must be APFS or Mac OS Extended and case-insensitive. A location on a disconnected drive is reported (`DistillerPaths.unavailable`) and never created in its place. After `moveStorage`, make a new engine.
- **Install steps the player can follow.** `InstallPlan.tasks` lists every step of an install before it starts, in plain words (creating the bottle, the Windows version, registry, graphics layer, each winetricks component on its own, then the recipe's steps), with a note on slow ones (.NET Framework can take half an hour or more with nothing on screen) and on installers that need the player. `RecipeInstaller` runs winetricks one component at a time and reports `InstallProgress.step` in that order; the app's `InstallProgressWindow` checks the steps off, shows the running one's elapsed time, and the CLI prints the list first. `InstallCancellation` stops an install: it stops every program in the new bottle (`wineserver -k`), and the install then removes the bottle (and an authored game's entry) and throws `CancellationError`, which the app doesn't report as an error.
- **When an install is done.** A `run_windows` step that waits returns when every program in the bottle has exited, or, for installers that start a launcher or the game and leave it running, as soon as the launch program exists and either something runs from its folder that isn't an installer (`RecipeInstaller.programStartedByInstaller`) or only Wine's own programs are left (`installFinished`; Wine's `wineserver -w`, polled with the bottle's process list). The second case matters because each poll (`wmic`) starts Wine's helper programs, which keeps the bottle from going idle: a silent installer that finished (Steam's) would otherwise be waited for forever. Afterwards `DistillerEngine.install` checks the launch program exists (`missingLaunchProgram`): an installer that was cancelled often exits normally, so the game is added (marked as missing its program, so it can be removed with its bottle) and the player is told.
- **Waits that would never end.** The .NET Framework's background compiler service (`mscorsvw.exe`, NGen) starts with the bottle and never exits under Wine, so any wait for every program to exit (Distiller's, and winetricks' own inside `dotnet40`/`dotnet48`) would hang forever after the installer finished. `StuckWait`: after 30 s of waiting, if only Wine's own programs and such services are left, Distiller sets the services to start on demand (`Start` = 3 in its registry key) and stops them (`net stop`). It finds winetricks' waits as `wineserver -w` processes under the winetricks process. Never stop anything else this way: while an installer, `msiexec`, `ngen` or the game runs, the wait is real. winetricks also runs with msync and esync off (`WineEnvironment.withoutFastSync`): under them the .NET Framework's compile workers stall forever after starting (ngen waits on them, the installer on ngen). Games keep the recipe's sync when played.
- **Installers run from the Windows drive.** Downloaded installers live in the bottle's `cache/`, outside `drive_c`, so Windows programs see them on `Z:` (Wine's view of the whole Mac). Some installers fail from there (Battle.net's setup can't reach its Agent: BLZBNTBTS0000005C), so `RecipeInstaller.onDriveC` clones any program outside `drive_c` into the Windows user's `Downloads` (`Public` if that user has no profile yet) and runs it from there, in installs and the community check. The cache keeps its copy for retries.
- **Games used in place.** A `user_folder` step can link a folder on another drive into the bottle (`C:\Games\<Title>` → the original) and map that volume to the next free drive letter from D: (`DriveMapper`), so the game reads and writes its original files. Never copy such a game silently.
- **Launchers and their games** (`Launchers/Launcher.swift`, `SteamLibrary.swift`, `BattleNetLibrary.swift`, `DistillerEngine+Steam.swift`, `DistillerEngine+SteamInstall.swift`, `AppModel+Launchers.swift`). A library entry whose launch program is a launcher's client (`LauncherKind.kind(ofClient:)`: Steam's `steam.exe`, Battle.net's `Battle.net Launcher.exe` or `Battle.net.exe`) is that launcher. `syncLauncherGames` (every reload, and every ~15 s in the app while a launcher exists) lists what each launcher has installed in its bottle: Steam from its app manifests (`appmanifest_<id>.acf`, `StateFlags` bit 4, a small VDF parser; not its redistributables or folders without a program), Battle.net from its Agent's `ProgramData\Battle.net\Agent\aggregate.json` (`product_id`, name, `icon_path`; listed once the program exists, since Blizzard games are playable while still downloading), plus its install database `product.db` (protobuf, `ProductDatabase`: product code and install folder), which also lists games the summary leaves out (Activision's), named after their folder. Each gets an entry sharing the bottle (`Game.launchedBy`: kind, the launcher's id for the game, the launcher entry, the program for the icon; Distiller 1.1's `steam` links are read into it on load), whose recipe starts it through the launcher (`launchArguments`: Steam `-applaunch <id>` then the player's own arguments; Battle.net `Battle.net.exe --exec=launch <code>`, `BattleNetLibrary.launchCode`, nothing else passed on); uninstalled games lose theirs; an unreadable bottle is left alone. A launcher game's bottle settings always follow the launcher's recipe (`aligned`), and saving it never writes the launcher's `recipe.yaml` or reconfigures the bottle; its own editable file is `recipe-<kind>-<id>.yaml` beside it (`recipeFileURL`). Running state isn't the process Distiller started (launchers hand launches over or restart themselves): a launcher counts as running while its bottle's wineserver is up, a Steam game while Steam's `logs/gameprocess_log.txt` says so (CRLF: split on any newline), a Battle.net game while a program from its folder runs in the bottle (`bottleProcesses`, from `ps -E`: Wine shows each Windows program's path; the game's own launcher stub doesn't count). Stop ends just the game (`taskkill` its PID or its programs); Remove asks Steam to uninstall it (`steam://uninstall/<id>`) or brings Battle.net up to do it there; removing a launcher removes its games' entries; a bottle another entry uses is never deleted. The library shows launchers with their games indented beneath (A to Z, collapsible); report prompts follow games, never launchers. A launcher entry's `Game.launcherOptions` (Steam: `LauncherOptions` start view and Friends status; the player's, on this Mac, never in a recipe): when Distiller starts Steam itself (its bottle isn't active), `launch(_:startingLauncher:)` puts `steamStartArguments` (`-nobigpicture`, `-gamepadui`) before the arguments and writes the Friends status into Steam's own saved one (`applySteamFriendsStatus`: `ePersonaState` in each account's `FriendStoreLocalPrefs_<account>` in `userdata/<account>/config/localconfig.vdf`, `SteamLibrary.settingPersonaState`). Tested on a real Steam under Sikarugir: `steam://friends/status/offline` doesn't sign out of Friends, `-silent` is ignored, and `steam://open/minigameslist` doesn't switch to Small Mode (Steam opens its full window once signed in), so Small Mode and menu bar only are read from earlier choices but not offered. Windows programs are placed in their bottle by working folder (`bottleProcesses`: they don't show WINEPREFIX), so `distiller bottles running` lists them. A Steam game's recipe (`SteamLibrary.gameAppID`: Steam's client with `-applaunch <id>`) is never installed into a bottle of its own (`install` refuses it): `installSteamGame` (app and CLI install) picks the Steam launcher in the library (same Wine family first), keeps the recipe in `SteamPending/<launcher>-<id>.yaml`, and asks Steam to install the app (`steam://install/<id>`, or applies it at once if Steam has it); `syncLauncherGames` applies a pending recipe's launch options, notes and name (`applying`) when the entry appears. Battle.net games' recipes aren't installed this way yet.
- **Recording performance** (`Performance/`, `PerformancePanel.swift`, `AppModel+Performance.swift`). A measured launch (`DistillerEngine.launch(_:measured:onOutput:onExit:)`, `MeasuredLaunch`) adds `MTL_HUD_ENABLED=1`, `MTL_HUD_LOG_ENABLED=1` and `MTL_HUD_OPACITY=0` as one-launch overrides: Apple's Metal HUD then writes `metal-HUD: <first frame>,<a>,<b>,<interval ms>,<gpu ms>,…` about once a second to the game's standard error (unredacted there; the unified log redacts the per-frame values). The overlay is transparent rather than hidden (`MTL_HUD_HIDDEN` stops the logging too), the variables only work when the process starts, and only Metal is seen (D3DMetal, DXMT, DXVK through MoltenVK; not WineD3D's OpenGL). `onOutput` feeds the game's output, as it arrives, to `FrameLogStream` (lines split across chunks; runaway lines dropped) and `PerformanceRecorder` (live frame rate; every frame between `start` and `stop`, per process, the game being the process that drew most). `PerformanceSummary`: average, 1% and 0.1% lows (the average rate of the slowest frames), median and 95th-percentile frame time, GPU time, a frame-time histogram (`bucketFPS`, edges with 1% slack because the HUD rounds), FPS per minute. The app's Record Performance… starts the game measured (or opens the panel for one already started that way; `settings.json` `record_performance_always` starts every game that way) and shows `PerformanceRecordingSession`'s floating panel (live FPS, Start/Stop, the player's `PlaySettings`, `GameDisplay`: window pixels and refresh rate from `CGWindowListCopyWindowInfo` and `NSScreen`); recordings are saved as `PerformanceRecord`s under `Performance/<game id>/` and never leave the Mac from there. Games started through Steam aren't supported yet (Steam starts them with its own environment). CLI: `launch --measure`, `performance summary`, `performance list`.
- **Keyboard settings** (`Wine/UserRegistryFile.swift`, `applyKeyboardSettings`). Wine's macOS driver reads `LeftCommandIsCtrl`/`RightCommandIsCtrl` and `LeftOptionIsAlt`/`RightOptionIsAlt` from `HKCU\Software\Wine\Mac Driver` when it starts; `settings.json` `command_as_ctrl` (absent = on) and `option_as_alt` (absent = off) are written into the bottle's `user.reg` directly (atomically, only those values) before every `launch` and `run`, because going through Wine's registry tool waits for the bottle to go idle, which never happens while a launcher runs. A bottle that's running picks changes up at its next start.
- **Shortcut apps** (`Shortcuts/ShortcutApp.swift`, `Support/ICNS.swift`, the `DistillerShortcut` target). Create Shortcut App… (and `distiller games shortcut`) makes `<Title>.app`: the `DistillerShortcut` program (shipped in `Contents/Helpers`, copied in), an `Info.plist` with `LSUIElement` (no Dock icon of its own while it waits; the game shows its own) and `LSApplicationCategoryType` games, the game's icon as `.icns` (`ICNS.make`: PNG entries 16–1024 px), `Contents/Resources/shortcut.json` (game id and title), signed for this Mac (`codesign -s -`); it only replaces an earlier shortcut. The program finds Distiller by bundle identifier, runs `Contents/Helpers/distiller launch <game> --from-shortcut` (which does nothing if `isGameRunning`) and waits, so the CLI records play time; on failure it shows the command's message and offers to open Distiller. Keep it dependency-free. The app marks games started outside it as running (`externallyRunning`, from `isGameRunning`: an ordinary game while its program runs in its bottle).
- **Editing recipe text.** The workshop's YAML tab uses `PlainTextEditor` (an `NSTextView` with every automatic substitution off: SwiftUI's TextEditor follows the system's smart quotes and dashes, which break YAML); use it for any file text. Edits in progress survive the game's recipe changing underneath (a save, a launcher sync). Open in Editor writes the tab's text to the game's recipe file and opens it; when Distiller is active again a newer file is loaded into the tab for Save YAML. A launcher game's launcher arguments are always rebuilt (`launchArguments`; for Steam `steamOptions` takes out every `-applaunch` and stray app ID wherever they ended up), on save, at launch and at each sync.
- **Library state.** `availability(of:)` reports ready / needs setup / unavailable with a reason; `launch` refuses with the same reason. Use `URL.followingSymlinks`, not `resolvingSymlinksInPath()`, which stops at a link whose target is missing.
- **Icons.** `PEIcon` reads a program's first icon group (through `PEImage`, the shared bounds-checked PE parser) and saves the largest image as PNG; a player-chosen icon wins. Icons stay out of recipes.
- **Authoring.** `RecipeDraft` turns builder choices into a `Recipe`; `GameInspector`/`PEFile` read a game's DLL imports to suggest settings; `ProgramFinder` ranks candidate programs; `TuningOptions` is the curated "Performance & display" list (each option is a recipe environment variable, documented for the version Distiller installs, with a link to that documentation).
- **Installer capture** (`Authoring/InstallerCapture.swift`, `InstallerCaptureView`). The workshop's Get from Download Page… opens the publisher's page in a WKWebView with a non-persistent data store that opens only https pages; the player clicks the download, and Distiller records the page, the clicked link, each redirect and the final address (`CapturedDownload`). `InstallerLinkTest` tries them in that order the way a later player's Distiller downloads, with no cookies and no referrer (HEAD, else a 1-byte GET; never a full download), skipping signed or expiring links and links serving a different size, and offers the first that works as `game.installer.url` (with the page as `game.installer.page`). `distiller recipe check-link` runs the same test. When none works, **Use the Download Page** keeps only the page.
- **Downloads from a publisher's page** (schema 2). A `user_download` step names a page and a `sha256` or `signer`; the player downloads the file there themselves, and it's checked before it's used (`RecipeInstaller.checkPageDownload`, again when the step runs). An installer with only `game.installer.page` is shared as a `user_download` (id `installer`) plus the run, and the community check gets it through `CommunityCheckPrompts.obtainInstaller`. The app opens the page in `PageDownloadWindow` (the capture browser in its checking mode, a window so it works over sheets; the file stays in a temporary folder until the install or check ends); the CLI prints the page and asks for the file's path (`--file <id>=<path>` for `install`). The catalogue publishes a page-only installer as `download_page` (`IndexGame.officialInstaller`, `officialInstaller()` on the website), because Distiller 1.0 can't read an index installer without a url. Shared recipes may only `user_download` from the game's own download page.
- **Publisher signatures** (`Support/Authenticode.swift`, `Support/DER.swift`). A download (and a `user_download`) carries a `sha256`, a `signer`, or both; with both, either passing is enough (`InstallerCheck`: the checksum first, then the signature, which still holds when the publisher ships a new installer; `Downloader.download(_:sha256:signer:to:)` keeps the file only after it passes). When only the signer passes, the install reports it (`InstallNotes.changedInstallers`) and the game records `installer_changed`, which the workshop shows its author until the community check runs again. The community check always records the checksum, plus the signer whenever the installer is validly signed (`CommunityCheckResult.installerSigner`); `game.installer.updates: true` makes a valid signature required. Recipes with both checks are schema 3, a `signer` alone (or an installer that `updates`, or a page download) schema 2, everything else schema 1 (`Recipe.requiredSchema`, `Recipe.baseSchema`), so older versions refuse what they can't check cleanly; Distiller reads all three (`Recipe.supportedSchema`). `Authenticode.verify` checks a Windows program's Authenticode signature, for installers that change with every update: the PE certificate table (data directory 4), the program digest (the file minus its checksum, certificate-table entry and table) against `SpcIndirectDataContent`, the signed attributes' `messageDigest` (over that content's value), the RSA or ECDSA signature with the certificate's key (`SecKeyVerifySignature`), the chain to a root macOS trusts (`SecTrust`; tests pass their own anchor), with soft-fail revocation checking, the code-signing EKU, and the signer's common name. A valid timestamp (`AuthenticodeTimestamp`: an RFC 3161 token or the older PKCS #9 countersignature, whose hash matches the signature, whose own signature verifies, from a certificate with the timestamping EKU whose chain was trusted at that time) makes the chain be checked as of the signing time, so installers signed while their certificate was valid stay valid after it expires (Steam's); a broken or untrusted timestamp is ignored, never trusted. Apple's CMS decoder doesn't accept Authenticode's PKCS #7, so `DERReader` (bounds-checked, DER only) parses it; `SignerInfoParts` reads signer records for the signature and its timestamps. Test fixtures are generated by `Tests/DistillerCoreTests/Fixtures/make-authenticode-fixtures.py` (a throwaway authority; no keys kept). `distiller recipe check-signature` runs it.
- **Community check** (`Authoring/CommunityCheck.swift`, `DistillerEngine+CommunityCheck.swift`). Proves a recipe works for other players before it's shared: a fresh bottle, the publisher's official installer (its SHA-256 recorded), the recipe's settings, then the installer started and the player in charge (`CommunityCheckSession`; nothing waits for the installer, which may start a launcher or the game and keep running). The player chooses the game's program from what's running in the bottle (`WineProcessList`: that bottle's Wine answers `wmic process get ExecutablePath,ProcessId`, since macOS's process list doesn't say which bottle a Windows program belongs to) or starts an installed one, and confirms it reached its login or menu; the chosen program becomes the launch program, and everything in the bottle is stopped. Shared recipes apply their settings steps before the installer. From the installer's start, the app's check panel and a global hotkey capture screenshots; images the game saves itself are collected too; the program's icon is read. Check bottles are named `<title> (community check)` and hold a `community-check.pid` file so interrupted checks can be found (`orphanedCommunityCheckBottles`).
- **Pictures.** `CommunityMedia` normalises icons (square PNG, at most 256 px) and screenshots (JPEG, at most 1600 px wide and 600 KB, no metadata). A recipe shares up to three screenshots (the first is the cover) and the game's icon.
- **Community catalogue.** `CommunityRepository.default` points at the published catalogue (`index.json`, per-game detail files, `media/`). `CommunityMatch` compares the player's games with it (new game, new recipe, changed, in review, published). The Community tab lists the catalogue's games and opens a page for each (`CommunityGameView`: screenshots, details, links, recipes with their settings, file and reports), like the website's game page; `CommunityGameDetail` decodes `games/<slug>.json` (test fixture `Fixtures/game-detail.json`, generated by `build_index.py` like `index.json`) and `CatalogueText` describes catalogue values the way `site/assets/catalogue-data.js` does. `CatalogueBrowser` filters (every search word; genre, graphics layer, minimum rating) and sorts (title, rating, recently reported) like that file's `filterGames`/`sortGames`/`facets`; its tests use the same games as the site's tests, so keep the two in step. Installing from a page, like a website link, goes through the confirmation sheet.
- **Submission** (`DistillerCommunity/GitHub`, `Submission`). The Submit window (`SubmitRecipeView`) is a checklist of steps (`SubmissionChecklist`: details, installer, community check, pictures, report, review), each done, needed, out of date or optional, worked out from the game and `SubmissionPlan.issues`; Submit needs no step needed or out of date. GitHub device-flow sign-in with the `public_repo` scope; the token lives in the keychain. `RecipeSubmitter` commits the recipe, an optional report, the game's catalogue file (first recipe only) and pictures to a new branch, then opens a pull request: on the contributor's fork, or on the repository itself for maintainers.
- **Links from the website** (`DistillerCommunity/DistillerLink.swift`, `AppModel+Links.swift`): `distiller://install?game=<slug>&recipe=<id>` and `distiller://game/<slug>`, registered in the bundle's Info.plist by `Scripts/bundle-app.sh`. A link only names a catalogue game and recipe; the app looks both up in the catalogue itself (downloading it again if needed) and shows a confirmation sheet. **Never act on a link without the player's confirmation, never accept anything but validated slugs, and never add link actions that take paths, URLs, commands or recipe content.**
- **Troubleshooting assistant.** `AssistantTools` are read-only tools (list games, read launch logs, read files in a game's folder or bottle, inspect a program, describe the environment), confined to the game's own folders, text only, size-capped, with the home folder shown as `~`. `MCPServer` serves them over stdio (JSON-RPC 2.0, one message per line) as `distiller mcp`, for MCP-capable assistants. The assistant is off until the player turns it on (`settings.json` `assistant_enabled`, absent means off); the server re-reads the switch on every request. Distiller never edits other apps' settings: the player adds `distiller mcp` to their AI app, which starts it. `MCPClientSetup` holds the connection steps and snippets (Claude Desktop, Claude Code, ChatGPT, LM Studio, Ollama, other stdio clients) shown by the app's connection guide (`AssistantConnectView`, opened from Settings ▸ AI Assistant) and `distiller assistant setup`; keep the website's docs (`site/docs/index.html#assistant`) in step with it.

## Rules that must hold

### Licensing and clean-room development

- **Distiller is MIT-licensed and clean-room.** Never copy, translate, port or paraphrase code (or tests, UI strings, or file formats' implementation details) from projects under copyleft licences (GPL, AGPL) or from proprietary software. That includes the projects that inspired Distiller: an archived GPL-3.0 macOS app that wrapped a commercial Wine fork with Apple's graphics layer, a GPL-3.0 Linux game manager whose shareable install scripts inspired recipes, and commercial Wine distributions. Learning from their public documentation and observable behaviour is fine; reproducing their code is not. Don't paste their source into a prompt or a tool to transform it.
- **Name things by function, not by product.** In code, docs and UI, describe other software by what it does and its licence (for example "a Wine build that exports the macOS driver functions"), except where a name is a technical necessity: a download source, a component Distiller installs, or an identifier in a published data format.
- **Dependencies must be MIT-compatible** (MIT, BSD, Apache-2.0, zlib and the like). No vendored copyleft code. Wine (LGPL-2.1) and copyleft graphics layers are only downloaded as separate components at the player's request and run as separate processes or libraries inside Wine; they're never linked into or shipped with Distiller.
- **Record the origin and licence** of anything not written for this project (assets, icons, snippets from permissively licensed sources) in a comment next to it.

### Apple software

- **Never bundle, host, upload, mirror or redistribute D3DMetal** or any other part of Apple's Game Porting Toolkit evaluation environment: nothing of Apple's is in this repository, the recipes repository or a Distiller release, and Distiller never fetches it from Apple for the player. Players import it from their own download from Apple (`GPTKImporter`). Distiller lists sources (`components/` in the recipes repository) and downloads from their publishers at the player's request; a third-party build that includes D3DMetal is that publisher's to answer for under Apple's terms, so its source is labelled (`contains_d3dmetal`), Distiller detects it after download (`MachODependencies.containsD3DMetal`), and the player is told before downloading a labelled source. Tests use placeholder files shaped like the real disk image, never Apple's.

### Recipes are data

- **No recipe can run a host command.** Install steps are a fixed set of verbs (download verified by SHA-256 or, schema 2, by its publisher's Authenticode `signer`; schema 2's `user_download`, a file the player downloads from an https page, verified the same way; copy, registry, winetricks from an allowlist, DLL overrides, running a Windows program inside Wine, asking the player for a file or folder). Every path in a recipe goes through `BottlePath.resolve` and must stay inside the bottle. Environment keys go through `RecipePolicy.isAllowedEnvKey` (Wine and graphics-layer tuning only, excluding anything that redirects Wine or loads host code).
- **Keep the safety lists in sync** between `RecipePolicy.swift` and the recipes repository's `schema/recipe.schema.json`: winetricks verbs, environment prefixes and denials, DLL override values, and the `user_folder` rule that matches `BottlePath.isInsideDriveC`.
- **YAML must read the same in Python.** The recipes repository validates with PyYAML. Yams writes some doubles in a form PyYAML reads as text (`6e+1`); write whole numbers as `Int` in files the repository validates.

### Sharing with the community

- **Shared recipes install from the publisher's official installer** (`game.installer.url`, HTTPS, never a mirror or re-hosted copy; `game.installer.page` is the publisher's download page, and on its own, schema 2, players download the installer there) and download nothing else of the game. Players may use their own copy locally (`user_folder`, `user_file`); those steps are swapped for the official installer when shared.
- **Shared recipes are MIT-licensed.** The submit sheet's licence confirmation is on by default and still required; pictures in `media/` stay the publisher's.
- **Only checked recipes are submitted.** A recipe is submitted only after the community check passed for its current content, and only the checked recipe (`CommunityCheck.recipeToSubmit`) is ever sent.
- **Submissions are pull requests on a new branch; nothing is ever pushed to the base branch.** Contributors' branches go in their fork; maintainers (GitHub reports push, maintain or admin permission) branch in the community repository itself. Never ask for more than the `public_repo` scope. A published recipe may be revised (an `-update` branch) only by a maintainer or one of the authors listed in the *published* file, never the player's own copy.
- **Keep formats in sync** with the recipes repository: `CommunityIndex.swift` with `scripts/build_index.py` (index schema, per-game fields, `HardwareProfile.hardwareKey`), `GameDetails` with `schema/game.schema.json`, and the picture limits and paths in `CommunityMedia.swift` with `build_index.py` (`media/<slug>/icon.png`, `media/<slug>/<recipe-id>/<1-3>.jpg`). The test fixture `Tests/DistillerCoreTests/Fixtures/index.json` is generated by that script: `python3 scripts/build_index.py --include-examples --out <tmp>/index.json`, then copy it in.
- **Pictures belong to the game's publisher.** Icons and screenshots are shared only to identify the game, are excluded from the MIT licence, and come from the player's own test run. Never add game files, art or screenshots of real games to this repository; tests use generated placeholders.

### Safety, privacy and honesty

- **Wine is not a sandbox.** Windows programs run with the player's permissions. Never describe Wine or a bottle as isolation or protection in UI text or docs.
- **No telemetry, analytics or crash upload** without an explicit, off-by-default opt-in. Compatibility reports are sent only when the player submits one, and contain only what the report form shows.
- **Release signing stays in the `release` environment.** The Developer ID certificate and the notary API key exist only as that environment's secrets, which need the owner's approval and accept only `main` and `v*` tags. Never add a `pull_request`, `pull_request_target` or other untrusted trigger to a workflow that uses them, never echo or upload them, and keep the temporary keychain's cleanup step running `if: always()`.
- **Secrets never enter the repository**: no tokens, passwords, private keys, signing certificates, provisioning profiles or API keys, not even in tests (use obvious fakes like `gho_test`). The GitHub OAuth client ID is public by design and may be committed; there is no client secret.
- **The MCP server's standard output carries protocol messages only.** Never `print` in code the server reaches; log to standard error.
- **Assistant tools stay read-only and confined** to the game's own folders, text only, size-capped, with the home folder shown as `~`. The assistant stays off by default, the server only speaks stdio (never make it listen on a network port), and Distiller doesn't write AI apps' configuration files.
- **Respect the player's machine.** Never write outside the support folder, the chosen storage locations and the player's bottles; never create folders on a disconnected drive; ask before deleting anything that isn't disposable (bottles, games, rescued screenshots).

### The website

- Catalogue data is written by the community: put it on the page only as text (`el()` in `site/assets/site.js` sets `textContent`), never as HTML. Follow only `https:` links and pictures under the catalogue's `media/` (the checks in `catalogue-data.js`), and build `distiller://` links only from validated slugs.
- No trackers, analytics, cookies or third-party scripts and fonts. Keep it static: no build step, no framework.
- Keep `catalogue-data.js` in step with the index format (`CommunityIndex.swift`, `build_index.py`), with tests in `site/tests/`.

### User interface

- Standard SwiftUI and AppKit controls and system styles, minimum macOS 14. No custom "glass" effects.
- Plain, specific language in UI text: say what happened and what the player can do. Name drives, files and games rather than "an error occurred".
- Long work shows progress in the status bar (`AppModel.perform`), and failures become an alert with the reason. Installs also open the install window, which lists every step; anything that can run for many minutes must say so and show that it's still working.

## The companion repository

`distiller-recipes` holds the recipe, game and report schemas, the recipes, reports, game catalogue files and pictures, and the scripts and workflows that validate them and publish the catalogue to GitHub Pages. Changes there follow the same rules: pull requests only, owner approval, and its Validate and Contribution scope checks. Its `README.md` and `CONTRIBUTING.md` explain the format and the rules for contributors.
